# cost-router：分而治之，按能力付费

## 核心前提

**不是所有任务都该拆。** 拆解本身要付分解费、汇总费，还会让文风断裂。只有"同时包含多种能力"的任务拆了才划算。

所以流程永远是：**先研判，再决定拆不拆，然后才动手**。

## 四个工具

| 工具 | 作用 | 花钱吗 |
|---|---|---|
| `cost_router_plan` | 研判 → 给出方案和预估 | 只有需要拆时才花一次分解费 |
| `cost_router_run` | 按方案执行 | 花 |
| `cost_router_report` | 看成本台账 | 不花 |
| `cost_router_models` | 看当前可用模型与哪些免费 | 不花 |

## 标准流程

### 1. 先 plan

```
调用 cost_router_plan，参数 task = 用户的完整原话
```

### 2. 看结论，分两种情况

**结论是"不拆"（mode: single）**
直接执行，不要跟用户提拆分的事。最多说一句"这活儿单一模型做更连贯"，然后干活。

**结论是"拆"（mode: decomposed）**
用 AskUserQuestion 把方案摆给用户，**只摆三样东西**：

- 拆成几块，每块干什么（一句话）
- 每块派给哪个模型
- 预估花费

选项给三个：① 按方案执行 ② 只用免费模型做（质量可能下降） ③ 取消，我直接干。

**不要把 subtasks 表格原样贴给用户**，也不要解释判断逻辑。用户要的是决定，不是过程。

### 3. 确认后 run

拿到用户选择再调 `cost_router_run`。执行完把结果给用户，最后附一行真实花费：

> 本次用了 5 次调用，合计 0.0123 相对成本（其中 3 次走免费模型）。

### 4. 需要解释时调 report

用户问"这次花了多少"、"为什么派这个模型"时，调 `cost_router_report`。

## 什么时候不要用

- 任务单一明确（"把这段改成正式公文"）——直接做，别绕
- 用户赶时间——分解是串行的，天然比单模型慢
- 任务短于 100 字——分解的判断成本超过收益
- 已经明确指定了模型——尊重用户

## 质量红线

拆完之后各写一段，拼起来容易出现"上半段一套话术、下半段另一套"。所以：

- `run` 的最后一步是汇总改写，**不要跳过**
- 汇总后自己通读一遍，检查人称、称谓、数字口径是否一致
- 发现断裂就再调一次汇总，别直接交

## 成本参考

编排省钱的原理是两条，缺一不可：

1. **单价差**：杂活落到便宜模型，能力不够时才升级到贵的
2. **上下文隔离**：每个子任务只带自己需要的材料，不把全文复制给每一路

第二条往往比第一条省得多。如果发现成本没降下来，先查是不是每个子任务都被塞了全部背景材料。

**相对成本的口径**：以"标准价模型跑同等 token"为 1.0。免费渠道的倍率是 0，所以免费模型干的活记 0。
